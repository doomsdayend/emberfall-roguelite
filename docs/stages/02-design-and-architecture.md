# 第 2 阶段 · 设计、架构与技术预研

日期：2026-10-12（北京时间）
账号／仓库：`doomsdayend/emberfall-roguelite`
交付性质：开发基础工程；未发布可玩版本
状态：设计与技术基础完成；运行、规则与 Linux 导出验证通过；图形和人工手感验收待补充

## 1. 本阶段目标与范围

把立项要求转成可实现的规则、模块边界和验证方法，并建立可启动、可导出的 Godot 工程。技术房用于验证基础输入、物理和暂停，不代替完整玩法。

本阶段没有敌人、攻击伤害、奖励选择、实际随机房间切换、首领或五槽存档。后续设计均在下面标记为“设计”，不能当作已实现功能。

## 2. 引擎、平台与运行基线

- 固定标准版 Godot `4.6.3.stable.official.7d41c59c4`，使用 GDScript，无 .NET 依赖。
- 编辑器与导出模板必须为同一版本；版本文件为 `.godot-version`。
- Compatibility 渲染；逻辑画布 1280×720，物理更新 60 Hz，窗口随画布缩放。
- 当前实际验证平台：本开发容器中的 Linux x86_64。不能据此宣称已验证 Ubuntu 桌面、Windows、低端电脑或 VMware 图形兼容性。
- Linux x86_64 导出配置已实现并验证；Windows 导出与图形兼容性尚未测试。
- 验证使用无窗口模式，没有在用户设备上打开游戏窗口。

采用成熟稳定分支中的固定补丁版本，避免开发过程随最新版漂移。后续升级引擎必须单独记录并重跑导入、规则、物理、存档和导出回归。

官方依据：
- [Godot 4.6.3 稳定版下载](https://godotengine.org/download/archive/4.6.3-stable/)
- [Godot 4.6 命令行文档](https://docs.godotengine.org/en/4.6/tutorials/editor/command_line_tutorial.html)

## 3. 操作与战斗规则

### 已实现的技术样例

| 操作／参数 | 规则 |
| --- | --- |
| 移动 | A/D 或左右方向键；最高速度 300 px/s；加速与减速 2400 px/s² |
| 跳跃 | Space；初始竖直速度 -600 px/s；重力 1600 px/s² |
| 离地宽限 | 0.10 秒，缓解刚离开平台时按跳跃失败 |
| 跳跃缓冲 | 0.12 秒，落地前按下可在落地时执行 |
| 闪避 | Shift；速度 680 px/s；持续 0.14 秒；冷却 0.7 秒；当前不提供伤害无敌 |
| 暂停 | Esc；冻结技术房物理与场景动画；UI 继续响应 |
| 返回菜单 | 清除暂停、销毁当前技术房；重新进入创建新玩家 |

技术样例的数值是可调基线，不是最终平衡结果。当前不能攻击。

### 第 3 阶段战斗设计

- 初始角色采用剑攻击；J／鼠标左键攻击，首次仅实现单次近战，不同时做复杂连招。
- 玩家初始生命 100，剑伤害 20。攻击前摇 0.08 秒、有效 0.10 秒、后摇 0.18 秒；命中框在有效期存在，一次攻击对同一敌人只结算一次。
- 玩家受击后给予 0.5 秒伤害保护，防止接触伤害每帧扣血；闪避有效期内的伤害保护在第 3 阶段单独验证。
- 敌人第一种为遗迹守卫：巡逻／追击 → 明确前摇 → 攻击 → 恢复。初始生命 40、伤害 10、前摇 0.45 秒；不允许无预警攻击。
- 攻击判定与视觉效果解耦。暂定敌我身体与攻击区域分别管理，环境、玩家、敌人、玩家命中框、敌人命中框使用独立碰撞层。
- 受击硬直、命中停顿、击退和震屏逐步加入并允许降低震屏强度；停顿不能破坏 UI、暂停或退出。
- 玩家生命降到 0 后只触发一次结算；清空房间敌人后开启出口。战斗中不得重复生成结算或奖励。

以上初始数值需要通过实际游玩调优，阶段文档记录每次改动的原因。

## 4. 单局流程与模块边界

流程状态：`MENU → PREPARATION → COMBAT → REWARD → COMBAT … → RESULTS`。返回菜单是显式边；非法跳转被拒绝且不改变当前状态。暂停使用 SceneTree 的独立暂停状态，不混入关卡进度枚举。

| 模块 | 当前实现 | 后续职责 |
| --- | --- | --- |
| SessionFlow | 状态枚举、合法跳转、随机种子保留 | 连接游戏流程与结算事件，不直接结算攻击伤害 |
| InputSetup | 基础键位初始化，避免重复绑定 | 键位设置、手柄支持 |
| PlayerController | 位移、跳跃、闪避、碰撞及原创占位图形 | 攻击状态、生命、伤害保护、角色技能 |
| TechnicalRoom | 安全技术房、平台、边界及分层占位场景 | 仅作技术验证；正式房间另建模板 |
| RoomPlan | 同种子可复现的房间计划 | 已生成房间记录、正式模板选择和可达性验证 |
| Main | 启动菜单、技术房入口、暂停和返回菜单 | 接入正式菜单、流程路由、HUD 与结算界面 |
| CombatResolver | 未实现 | 过滤队伍与无敌、去重命中、结算伤害并发出事件 |
| RewardService | 未实现 | 按构筑生成奖励，记录已领取状态，不重复抽取 |
| SaveService | 未实现 | 五槽存档、格式版本、原子写入和迁移 |

控制器不直接读写存档；奖励服务不操纵菜单节点；场景表现通过事件读取战斗结果。先使用清楚的小模块，避免为尚未实现的功能建立大规模抽象框架。

## 5. 房间与随机性设计

已实现 `RoomPlan.generate(seed, combat_count)`：计划以安全房开始，以首领房结束，中间为确定性选择的战斗模板。默认三间战斗房；计数限制为 1–12。该接口当前只生成数据，不实例化正式房间，也不说明路径已可玩。

第 3 阶段先使用两个固定战斗房，减少同时调试随机生成和战斗的复杂度。第 5 阶段再接入模块化随机组合。

正式房间模板至少声明：房间 ID、入口／出口锚点、可站立地形、敌人刷新区域、禁止刷怪区域、障碍候选点、相机范围和奖励位置。

随机障碍不得挡住入口、出口、必经路径或把玩家生成在实体中；选不出合规候选时跳过障碍，而不是强行生成。房间和奖励使用单独派生种子，避免增加视觉随机粒子后改变关卡结果。

继续游戏保存房间序列、已清除敌人、已取奖励和当前构筑；不能只保存种子后重新生成整局。

## 6. 装备、构筑、角色与难度设计

下列在第 4–6 阶段实现，当前工程没有这些内容：

- 武器：剑提供近距离节奏；第二种武器为远程法器，使用不同发射与命中逻辑，不能只替换颜色。
- 增益初始候选：攻击范围增加、击杀回少量生命、闪避后强化下一击；涉及触发频率的效果必须有冷却或上限。
- 负面效果初始候选：最大生命下降但攻击增强、奖励提高但敌人更快；选择前显示实际收益和代价。
- 角色：先把一个角色做完整；第二个角色在技能、轮廓、动作和武器适配上区别，不只调整数值。
- 难度：设计普通／挑战两个等级；首个原型只实现普通。挑战优先调整敌人组合和攻击频率，避免纯粹堆生命。
- 永久进度优先用于解锁武器、角色或规则变化；数值成长设置上限，防止初始难度依赖长期刷取。

## 7. 五槽存档设计

当前未实现。拟使用 `user://saves/slot_01.json` 至 `slot_05.json`，不把用户进度放进源码仓库。

每槽包含：`schema_version`、游戏版本、最后保存时间、角色、难度、永久解锁，以及可选的 `active_run`。单局包含种子、房间计划、房间状态、玩家生命、装备与增益、已领取奖励。时间记录使用 UTC，界面按本地时间显示。

保存流程：序列化 → 写同目录临时文件 → 校验可读取 → 保留上一份备份 → 替换正式文件。写入失败必须保留上一份有效存档并提示失败，不能声称已保存。

退出暂停菜单时保存仅在合法安全点执行；战斗途中继续游戏的恢复规则在第 5 阶段明确。死亡清除该槽的进行中单局，保留永久解锁，不影响其他槽。格式升级逐版迁移；未知更高版本存档拒绝覆盖。

## 8. 美术、动画与声音方向

当前技术房采用原创程序绘制：冷色远山、废墟立柱、暖色灯笼与灰烬粒子，红色披风突出角色轮廓。角色有简单步行摆动和闪避拖尾。这些是构图候选与动作占位，不是正式美术样板验收。

正式视觉质量在第 4 阶段建立：

- 使用统一的比例、光线方向和材质表现；远、中、近景在亮度与移动速度上有层次。
- 角色至少有待机、跑、起跳／空中／落地、攻击、闪避、受击、死亡动作；有明确预备、执行和恢复。
- 披风、头发和环境细节随动作与风变化；不把整张静态图片左右抖动当成完整动画。
- 特效服从攻击轨迹与命中时刻，粒子数量和亮度有预算；危险预警始终清晰。
- 音效至少覆盖移动、跳跃、攻击、命中、受击、死亡、奖励和 UI；暂停与退出不遗留播放状态。

当前没有音效，也没有人工图形与手感验收。不得据无窗口测试把美术标为通过。开发界面暂为英文；第 3 阶段引入许可明确的中文字体并建立中文菜单。
