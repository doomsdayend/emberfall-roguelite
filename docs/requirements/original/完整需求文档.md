# 横版 2D 动作肉鸽游戏分阶段需求文档

文档版本：1.0 ｜编写日期：2026-10-12 ｜状态：可用于新项目立项与分阶段开发。

本项目从零建立新的横版 2D 动作肉鸽游戏。核心体验是动作连贯、攻击有力度、角色有鲜明外形与完整动画、随机构筑能改变操作方式。本文档包只规定需求、交付物和验收条件，不包含游戏代码，也不代表仓库或游戏版本已经创建。

## 默认方案与范围

- 目标平台：Ubuntu 24.04 x86_64 桌面；首发不要求 Windows、移动端、浏览器或联机。
- 类型：横版视角、单人、房间式探索与战斗，平台跳跃作为空间战斗辅助手段。
- 暂定题材：原创幻想世界中的余烬遗迹。名称与世界观可在阶段 1 调整，禁止直接使用商业游戏角色、地图或音频。
- 美术：精致手绘 2D 角色，骨骼动画结合局部逐帧动画；动态光影、景深分层和环境动画。不是默认像素风，也不以几何图形换色作为最终角色。
- 控制：键盘鼠标与手柄；第一版就有暂停、返回标题、失败与重新开始。
- 正式版目标：3 名角色、6 个武器家族、3 个区域、3 名首领、普通与精英敌人、正面增益和可选择的负面代价、5 个存档槽位。
- 正式版单局目标 25—40 分钟。此时长、动作时间与数量是设计初值，实际平衡需通过试玩收敛。
- 引擎和具体动画工具在阶段 1 冻结，须支持 Linux 导出、状态机、2D 骨骼或精灵动画、数据驱动和可复现构建。可评估 Godot、Unity 或其他合适方案；不因未选引擎阻止文档使用。

以上是本需求采用的默认设计，不是用户已确认的引擎、美术成品或最终设备性能。阶段 1 必须把调整后的结果写入决策记录，避免中途无记录换方向。

## 全程必须遵守

1. 每阶段先读该阶段文档、总需求、角色动作规范和发布规范；只推进已通过依赖验收的内容。
2. 每个可游玩版本必须在干净目标环境安装启动，从标题进入并完成该版本声明的流程；原型不要求拥有正式版全部内容。
3. 角色造型、姿势与行为动画必须形成一致体系；同一动作不能靠拉伸人物、整张图片平移或只更换特效来冒充。
4. 每次发布都有可下载构建、源码提交、Git 标签、更新说明、测试报告、已知问题、存档兼容说明和 SHA-256。
5. 使用当前已绑定 GitHub 账号 `doomsdayend`。暂定新仓库名 `emberbound-2d-roguelite`，该名称未检查占用、仓库尚未创建。默认私有；若环境不能创建或账号不符，记录阻塞并请求用户解决，不冒用其他身份或在无关旧仓库写入。
6. 本次不创建仓库、不推送代码、不发布游戏；GitHub 连接与持续记录是后续开发执行要求。
7. 最终美术资产须有制作源文件、导出文件、许可证或原创说明。不得把其他游戏截图拆成素材。
8. 用户设备上不得自动弹出游戏窗口。自动验证用适用的无界面方式；需要人工窗口试玩时由用户自行启动。

# 阶段 1 立项与预制作

目标：在投入程序和批量美术前，确定游戏要做成什么、最小验证范围是什么，以及怎样判断完成。此阶段产出方案与设计资产，不发布可游玩版本。

## 进入条件

已经阅读总需求；识别本次是全新项目，不默认继承旧项目架构或角色资产。允许借鉴过去的经验，但任何复用都须记录来源和适配工作。

## 产品设计

形成简明 GDD，至少覆盖：体验目标、玩家画像、控制方式、核心循环、失败与永久成长、角色差异、战斗距离、地图结构、武器、增益与代价、难度、存档、界面、内容数量、交付平台。

核心循环固定为：选择存档 → 选择角色和难度 → 安全初始房间 → 选择起始武器 → 探索战斗和构筑 → 首领 → 区域推进 → 胜利或死亡结算 → 永久解锁 → 再次出发。首局不能直接进入怪物围攻。

正式版优先级：

| 等级 | 范围 | 处理方式 |
| --- | --- | --- |
| 必须 | 流畅移动、战斗、角色动画、3 区域主线、存档、暂停退出、可安装发布 | 发布缺失即不通过 |
| 应有 | 手柄、设置、图鉴、训练场、帮助与可读性选项 | 正式版前完成，裁剪必须修订需求 |
| 延后 | 联机、创意工坊、复杂剧情演出、每日在线挑战、无限关卡 | 不进入首发关键路径 |

## 角色和美术预制作

先完成主角“烬刃”的侧视标准模型、比例标尺、前后或三分之四参考、表情、配色和武器尺寸。动作概念至少画出待机、跑步接地、起跳、最高点、落地、攻击预备、命中、收势、翻滚、受击、死亡的关键姿势。

同屏给出主角、近战敌人、远程敌人与大型首领的剪影比较。以 1280×720 实际游戏视角验收，不能只展示放大的立绘。

环境概念展示三个区域的色彩、材质、光源、前中后景层次和可交互物的识别方式。界面必须与环境风格统一；战斗区不能被复杂背景和装饰遮挡。

## 技术和资源路线

- 比较引擎的 Linux 导出、资产导入、动画事件、工具维护、授权成本和构建自动化，选定具体版本并记录理由。不是默认追求最新版。
- 选定角色动画路线：骨骼为基础，手绘逐帧补充攻击、表情和特效；若纯逐帧质量与成本更合适，可采用纯逐帧，但所有动作验收不降级。
- 明确最小设备档位并记录 CPU、GPU、RAM、分辨率、驱动。60 FPS 目标绑定具体测试机，未测量不得宣称支持任意 Linux 设备。
- 原生基准画面 1280×720；适配 1920×1080 和常见宽高比，镜头有效视野不能因比例扩大而破坏战斗设计。
- 世界尺度：主角站立碰撞高度定义为 1H。移动和场景距离以 H 或引擎单位描述，贴图像素不直接决定物理尺寸。
- 列出模块边界：输入、角色控制、战斗结算、动画、敌人 AI、地图生成、物品构筑、存档、UI、音频、构建。
- 设计数据表字段、存档 schema、资产命名、版本记录和异常日志策略，具体实现留到后续阶段。

## GitHub 初始化要求

读取当前连接身份，确认 `doomsdayend`；创建或选择属于该账号的专用新仓库，不覆盖旧项目。初始化 README、docs、任务清单、资产授权记录、CHANGELOG 和忽略规则；动画源文件等大二进制采用适用的大文件管理方案。权限、工具不可用时明确记录未连接，不伪造成功。

## 交付与验收

交付：GDD、项目范围清单、技术决策、首批角色设定、环境概念、动作清单、风险登记、仓库信息和阶段 2 任务列表。

通过条件：核心循环明确；每个首发需求有阶段和验收方法；主角关键姿势与尺寸统一；引擎和动画工具可完成一次最小资产导入及 Linux 导出验证；仓库账号和路径有真实核验；成本、性能与资产来源风险有处理方案。

禁止在范围和美术标准仍模糊时批量生成数百素材。若一阶段无法解决技术导出或角色动画路线，先解决阻塞，不能以“后续完善”进入内容量产。

# 阶段 2 动作原型与基础闭环

目标：发布 v0.1.0，证明移动、跳跃、攻击与闪避形成可操作的战斗。美术允许占位，但必须表达姿势和时序，不能仅用静态方块代表动作。

## 最小可游玩范围

标题、开始游戏、简版设置、安全初始房间、训练区、2 个固定战斗房间、1 个测试首领或精英终战、胜利和死亡结算、暂停、返回标题、重新开始。1 名角色、1 种武器、2 种敌人。至少能连续完成两轮而不重启应用。

## 控制与运动

| 输入 | 默认键位 | 需求 |
| --- | --- | --- |
| 左右移动 | A/D 或方向键 | 加速与减速可调，松手反馈清楚 |
| 跳跃 | Space | 轻按短跳、长按高跳；单向平台向下穿越 |
| 普通攻击 | 鼠标左键 / J | 三段连击，输入缓冲，命中明确 |
| 技能 | 鼠标右键 / K | 阶段 2 可为简单重击，但须有独立动画 |
| 闪避 | Shift / L | 有资源或冷却约束，明确无敌时窗 |
| 交互 | E | 仅在交互范围触发，不与战斗输入冲突 |
| 暂停 | Esc | 停止战斗计时、AI 和伤害，继续无输入泄漏 |

初始调参：移动约 4.5—6H/s；跳跃高度约 2—2.5H；土狼时间 80—120ms；输入缓冲 100—150ms；闪避总长约 300—400ms，无敌段约 120—180ms。均须列出实际定值并通过试玩调整，不把范围直接写成不可解释的随机变化。

要求：低帧率下运动不明显变慢；斜坡、墙角、落地和单向平台无卡住；不能用关闭碰撞实现常规闪避；跳跃上升、最高点、下降和落地各有对应状态；翻向不重置连击或跳跃状态。

## 战斗和判定

普通连击包含预备、生效、收势，各段独立配置伤害、击退、命中框与动画事件。初值可采用 300/360/480ms 总时长，第三击更重；这些是动作设计起点，不是必须照搬的最终平衡。

受击区、攻击区、实体碰撞区分离。攻击命中由规定生效段驱动；同一攻击实例对同一目标默认仅结算一次。无敌期间不能扣血，死亡目标不能继续攻击。存在多个伤害来源时有清楚的叠加、免疫和受击优先级规则。

命中反馈包含轻重有别的停顿、受击姿势、音效、少量粒子与可关闭震屏。停顿建议轻击 30—50ms、重击 60—90ms 起测；不得让连续命中导致长时间无法操作或将暂停等同命中停顿。

敌人至少包括近战追击者和远程射手，均有察觉、接近或瞄准、预警、攻击、生效、恢复、受击、死亡。预警与攻击方向一致，不允许瞬间无提示命中。

## 原型验收

- 30/60/120 FPS 限制下分别验证移动距离、跳跃高度和攻击节奏；用可记录结果说明差异是否达标。
- 测试边缘起跳、松键短跳、落地缓冲跳、快速转向、被击中打断、连击接闪避和空中攻击。
- 进行至少 20 次房间重开和 10 次完整原型流程，未出现卡死、门不开、死亡后仍攻击或回标题失效。
- 暂停和失焦不会继续扣血；按住攻击返回游戏不触发意外攻击。
- 调试视图能显示碰撞框、动作状态、动画事件和攻击实例；玩家发布版默认隐藏。

交付：Linux 可安装构建、操作说明、实际动作参数表、状态转换与优先级记录、试玩结果、已知问题和 v0.1.0 更新说明。严格按附件 B 发布，标注“固定房间原型”，不宣称完成随机肉鸽。

# 阶段 3 角色制作与垂直切片

目标：发布 v0.2.0。以 8—12 分钟短流程展示最终美术方向和战斗品质，同时验证角色资产生产流程。

## 范围

保留可玩闭环，完成 1 名最终品质主角、1 个最终品质武器家族、3 种敌人、1 个精英、1 名完整首领、1 个区域场景与 6—8 个房间模块。加入少量可改变战斗的增益供验证；本阶段仍可使用固定或有限随机流程，不提前承诺完整肉鸽系统。

## 主角制作

按附件 A 完成烬刃的模型设定、分层源文件、骨骼绑定或逐帧制作、全部基础动作、三段地面攻击、空中攻击、角色技能、武器插槽、受击与死亡。

必须提交“姿势预览”和“实机动作预览”：前者用于检查比例与轮廓，后者在实际镜头与场景中检查可读性、接地和方向。动画在干净背景上好看而实机看不清，不算通过。

骨骼制作须避免手臂拉长、肘膝反折、关节穿帮、衣服与身体脱节；头发、衣摆、披风有与速度一致的次级运动。攻击必须由腿、髋、躯干、肩、手臂共同发力，不能只有武器绕人物转圈。

## 敌人及首领

三类普通敌人至少覆盖近战、投射、位移。精英具备明显轮廓和独特行为。首领至少 3 个招式、明确预警与攻击后窗口；第二阶段改变行为组合，不能只把颜色变红和数值翻倍。

首领招式需求表记录：距离、朝向、预警时长、有效区、恢复时长、可闪避方式、打断与免疫规则、阶段切换。跳跃或闪避应有可理解的应对方式，不依赖事先背板才能判断伤害来源。

## 场景与反馈

完成背景远景、中景、玩法层、少量前景；近景遮挡人物时自动淡化或避免占据战斗区。环境有火焰、尘埃、草木等节制动态，运动方向与光源一致。

主角、敌人和背景形成亮度与轮廓区别。攻击特效贴合动作轨迹，刀光从真实武器挥动方向产生；脚步、落地、材质命中、击杀音效匹配事件。摄像机提供移动前视、有限纵向跟随、首领边界及轻量震动设置，不在落地时剧烈抖动。

## 通过条件

- 实机中能够一眼区分待机、跑步、闪避、攻击、受击和死亡。
- 动画源文件可修改与再次导出，模型规格、插槽、锚点、材质和命名符合附件 A。
- 以实机 1 倍尺寸录制完整关卡和动作展示；慢放检查攻击时窗与实际武器轨迹一致。
- 地面奔跑接地自然，攻击不改变身体尺寸，翻向不造成武器插槽错位。
- 首领预警、伤害范围、胜利门与结算均经过测试。
- 在阶段 1 确定测试机上测量运行表现，记录性能瓶颈和后续预算，禁止仅展示单张精美截图。

交付：v0.2.0 构建、模型设定与动画源文件、资产登记、切片演示、镜头与音画参数、品质审核及更新说明。此阶段通过后，才能按同一标准批量生产后续角色和敌人。

# 阶段 4 随机关卡与肉鸽循环

目标：发布 v0.3.0，完成一名角色的一局单区域肉鸽，验证随机性、构筑、死亡重来和存档恢复。

## 房间与生成规则

单区域一局约 10—15 分钟，包含安全初始房、战斗、奖励、商店、事件、精英和首领房。房间用经过验证的模块组合，障碍、敌人与奖励从约束数据生成，不随机摆放到角色落点、传送门或无法到达位置。

生成数据包含种子、算法版本、房间连接、障碍布局、敌人组合、奖励池和必要参数。调试可重现给定版本与种子的地图；跨算法版本不保证生成结果一致，需在记录中写明。

连通验证须考虑主角基础能力，不得要求尚未获得的二段跳或特定角色技能才能走主线。战斗门在清场后解锁；敌人跌出边界或不可达时要恢复或按规则处理，不能永久锁门。陷阱、平台和掉落都有视觉提示及防软锁规则。

## 武器、装备和构筑

本阶段至少 2 个武器家族、12 个正面增益、4 个可选择代价、3 类实际构筑路线，如近战连击、投射物控制、闪避触发。

统一术语：武器决定攻击形态；装备提供基础属性及词条；遗物提供机制；增益为单局强化；诅咒或代价提供风险收益。暂定 1 个主武器槽、1 个护甲槽、2 个饰品槽和 6 个遗物槽。增益上限与替换规则须显示；同名重复升级和叠加上限必须有描述。

收益选择通常给出 3 项，可对比当前效果与升级后效果。代价在选择前显示具体影响，例如生命上限降低换取攻击范围提升；新手难度不强制未知负面效果。增益应影响轨迹、时机、操作或构筑，不能全部只是“伤害 +5%”。

数值顺序、概率上限、触发冷却和相互作用写入设计表。对攻击触发新攻击、再次命中触发、反伤或连锁效果明确触发深度与次数限制，避免无限递归。

## 永久成长与难度

死亡清除本局装备和增益，保留本局获得且按结算规则确认的永久货币、角色或武器解锁。首领击杀和结算须去重，防止重载刷取奖励。永久成长以解锁选择和少量基础提升为主，不以无限数值碾压替代动作体验。

提供休闲、标准、挑战三档，说明敌人压力、资源和辅助机制差异。不能只倍增生命延长战斗。难度选择进入局前完成，本阶段不要求局中切换。

## 五存档槽位

- 标题显示 5 个独立槽位，包含角色解锁、累计时长、最近时间、游戏版本与进行中状态。
- 区分账户配置、永久成长和本局快照；删除槽位必须二次确认，不能误删全部档。
- 可在安全房或清场后的检查点存储本局快照；退出后继续恢复到最近检查点，UI 明确说明，不承诺任意战斗瞬间恢复。
- 快照至少保存角色、生命与资源、装备、增益、种子和生成版本、已完成房间、当前位置与结算状态。恢复不重复刷新已领取奖励。
- 保存采用原子替换和至少 1 份有效备份；损坏时提示恢复或新建，不静默覆盖。
- schema 有版本号；升级迁移有备份；不兼容的活动局需告知如何处理，不能擅自清空永久成长。

## 验收

以不少于 200 个种子自动或工具辅助验证连通、可达、首领可进入与奖励合法；另选至少 20 个种子人工试玩。抽测不同角色尺寸与基础跳跃能力，覆盖障碍边界。

五槽位逐个测试新建、存档、退出、恢复、死亡结算和删除。验证暂停不推进 RNG、冷却、伤害和房间计时。覆盖写入中断、重复加载、无剩余空间和损坏档恢复。

交付：v0.3.0 构建、生成规则、种子测试记录、构筑与数值表、存档 schema/迁移说明、已知问题和更新记录。必须可从安全初始房完成单区域首领并结算。

# 阶段 5 内容生产与完整流程

目标：发布 v0.5.0 Alpha，形成完整三区域流程。新角色、武器和敌人可有明确标记的临时资产，但行为、判定、数据和流程必须完整；角色主动作不能仍是单张站姿。

## 首发内容规模

| 类型 | 目标 | 差异要求 |
| --- | --- | --- |
| 玩家角色 | 3 名 | 轮廓、体态、技能、资源循环和至少部分独特动作 |
| 武器家族 | 6 类 | 短刃、重剑、长枪、弓、符铳、法器，各有独立动作及攻击轨迹 |
| 武器物品 | 至少 18 件 | 每家族至少 3 件，提供实质词条或机制差异 |
| 区域 | 3 个 | 地形、敌人组合、环境危险和配色不同 |
| 房间模块 | 每区域至少 12 个 | 不把仅换色算新模块 |
| 普通敌人 | 9 类 | 近战、远程、飞行、护盾、位移、召唤等行为组合 |
| 精英 | 3 类 | 各区域至少 1 类，有独特攻击或组合 |
| 首领 | 3 名 | 各区域 1 名；最终首领提供完整结局 |
| 增益 | 至少 30 项 | 含 3 条以上机制构筑路线 |
| 代价/诅咒 | 至少 10 项 | 风险、收益、叠加、解除规则可读 |
| 遗物 | 至少 12 件 | 修改机制，明确槽位和互斥 |
| 装备 | 至少 12 件 | 护甲与饰品，图标和穿戴规则明确 |
| 事件 | 至少 8 种 | 有明确选择、收益与代价，不全是文字换数值 |

数量统计以行为或功能不同的条目为准，不重复把换色和品质等级计算为新机制。

## 三名角色定义

- 烬刃：近战平衡型，前压、连击、招架或反击；短发与短披肩轮廓，重心偏前，干脆姿态。
- 风弦：远程敏捷型，蓄力弓与轻型投射、空中调整或位移技能；长发、轻装与长弓轮廓，动作轻快但落地有重量。
- 星契：法术控制型，符印或法器攻击、短距离瞬移或区域技能；宽袖、法器与悬浮装饰，施法有蓄势和收势，不全程漂浮替代步行动画。

角色技能与特性在选择页面描述，支持未解锁预览。所有角色可以使用公共武器家族，但需要兼容的握持插槽与姿态；专属技能不因换武器丢失。共享动画可以复用结构，必须适配体态、服装、身高及发力节奏，不能只换皮。

## 内容生产要求

每项内容有唯一 ID、显示名、图标、说明、基础数值、叠加/解锁规则、音画资产引用和测试状态。武器定义地面、空中、技能及强化交互；挥砍、突刺、箭矢、散射、穿透、弹跳、法术区域具备可识别轨迹。

区域推进规则明确：商店与事件分布有上限，稀有奖励有保底或透明设计，最终流程不因随机生成缺房而中断。新区域进入有短过渡，首领击杀结算与永久奖励不重复。

提供图鉴、基础教程、角色和武器解锁反馈。正式流程至少有一个可理解的结局画面，胜利后可以继续新局，不能停在不可操作的结束文字。

## Alpha 验收

3 角色 × 3 难度分别完成至少 1 次三区域流程；6 个武器家族分别完成至少 1 次全局。极端构筑验证连锁、穿透、反伤、召唤和多投射物同时发生时不会软锁或递归失控。

逐项检查内容表、动画引用和解锁路径；无缺失动作状态、不可读取物品、不可购买商品或首领门卡死。标出尚未精修的资产，但不存在以占位 UI 隐藏玩法缺失的情况。

交付：v0.5.0 构建、全内容目录、解锁和数值表、9 个组合试玩结果、资产缺口清单及更新说明。范围新增必须记录成本和受影响阶段，不无限扩充首发。

# 阶段 6 美术表现与体验打磨

目标：发布 v0.8.0 Beta，让完整游戏拥有统一、灵动、清晰的视觉表现，完成全部正式角色、敌人、武器和环境资产。

## 全量资产精修

附件 A 的造型、动作、转向、握持、碰撞和输出标准覆盖所有主角和敌人。建立资产审核清单；缺省动画、静态死亡、武器错位、未授权音画资产为阻塞问题。逐个替换 Alpha 临时资产，不能只有开始页面精美而游戏本体仍全是占位图。

服饰、发丝、绳索、武器挂件的次级运动随动作变化：起步滞后、急停前摆、落地回弹、转向跟随，幅度克制。呼吸和站姿有微变化，禁止整个人物周期性缩放冒充呼吸。

动作衔接覆盖跑转攻击、空中转攻击、攻击转闪避、闪避转跑、落地转连击、受击转死亡。保持轮廓可读，必要时补过渡姿势；混合不能让脚穿地、肢体旋转过大或攻击命中时武器尚未挥到。

## 场景与镜头

三区域各有独特材质和环境运动，不依赖全屏滤镜区分。玩法平台边缘、陷阱、门、可破坏物与装饰层有视觉语法。传送和出口有明确引导。

镜头包含速度前视、首领锁区和边缘约束；宽高比适配不露出未制作场景。前景必要时淡化，背景视差不干扰高速运动。攻击震屏、强光、残影、伤害数字可调，提供降低闪烁选项。

粒子、光照和后处理设数量预算与距离裁剪；全屏爆炸不得遮蔽敌人预警。颜色之外同时使用形状、动画或标志区别友军、敌方投射物和危险区域。

## 音频与界面

脚步按材质，挥空与命中不同，轻重伤害不同，技能充能、资源不足和冷却完成有反馈。音乐与环境声分层，连续重复音效限制叠加。音量设置分主音量、音乐、效果，可即时预览。

标题展示动态但低干扰的角色或场景；角色选择展示真实动作而非单张卡面。存档、难度、装备对比、增益选择、暂停、死亡和胜利界面统一排版，避免原始调试文本。完整中文字体与必要英文技术文字不乱码。

提供键位重映射、手柄提示自动切换、屏幕模式、分辨率、画质、震屏、闪烁与伤害数字设置。失焦自动暂停，窗口关闭按存档规范处理，设置即时保存且不写入活动局随机状态。

## Beta 验收

实际镜头尺寸逐项审核所有动作；静音状态仍能识别敌人预警；关闭震屏与粒子强化后战斗信息仍完整。1280×720、1920×1080 及约定宽高比无 UI 遮挡或文字截断。

至少邀请 3—5 名未参与实现的试玩者完成起始房和首个区域；记录误操作、看不懂的攻击、找不到出口与动作迟滞。自动测试不能替代手感反馈；若没有真人试玩，必须标为待验收，不能伪称已做。

交付：v0.8.0 构建、最终资产清单、动作演示、音画 QA、试玩报告、性能数据及更新说明。所有影响战斗可读性的表现问题进入修复，不因“效果华丽”免除。

# 阶段 7 测试优化与正式发布

目标：先发布 v0.9.0 候选版，通过回归和质量门禁后发布 v1.0.0。正式版为完整可玩、安装清楚、存档可靠的 Linux 单机游戏。

## 测试范围

| 类别 | 必测项 | 证据 |
| --- | --- | --- |
| 安装启动 | 干净 Ubuntu 环境、无需开发引擎、路径含空格或中文 | 环境和步骤记录 |
| 完整流程 | 3 角色、3 难度、6 武器家族、3 区域、全部首领 | 组合测试矩阵 |
| 动作判定 | 时窗、取消、无敌、打断、翻向、空中和落地 | 慢放和调试事件记录 |
| 随机地图 | 连通、障碍合法、房门、掉落和边界恢复 | 种子及算法版本 |
| 存档 | 五槽位、检查点、升级迁移、损坏、写入中断 | 备份与恢复结果 |
| 系统输入 | 键鼠、手柄热插拔、重映射、失焦、暂停、关闭 | 实机结果 |
| 极限效果 | 大量投射物、连锁、召唤、持续伤害 | 最坏场景性能记录 |
| 长时间运行 | 2 小时连续游戏、50 次房间切换、20 次重开 | 内存与错误日志 |

至少覆盖代表性 300 个种子的工具验证和 30 个种子的人工地图检查；可复用已有可信记录，但改动生成算法后必须重新验证受影响范围。

## 性能门槛

在阶段 1 冻结的基准测试机、约定分辨率和标准画质上，普通战斗目标 60 FPS；记录帧时间中位数、P95/P99、超预算帧比例、峰值内存与加载耗时。建议门槛 P95 帧时间不超过 20ms，连续低于 45 FPS 超过 1 秒视为问题；初始目标须在立项确定后被冻结或经记录修订。

不能只报平均帧率。记录测试机、构建 SHA、场景种子、角色和构筑。检查长时间运行后内存是否持续增长，纹理、粒子、对象池及音效是否释放。

资源加载需避免战斗中明显停顿；加载屏显示合理进度或状态，不假装立即完成。不能以降低动画帧或取消敌人预警换取性能通过。

## 缺陷分级与发布门禁

- P0：无法启动、崩溃、存档丢失、无法通关、严重越权或资产泄露，必须修复。
- P1：核心战斗错判、持续卡顿、软锁、关键 UI 或输入失效，必须修复。
- P2：局部表现、数值或一般体验问题；明确是否影响正式体验，未修复项写入已知问题。
- P3：小瑕疵和建议，记录排期。

正式版 P0/P1 必须为零；首发内容和角色动画清单必须完成。自动验证和人工验证分别标记，不得以“测试脚本已写”代替已运行。

## 发布交付

每次 RC 和正式发布分别提供：Linux x86_64 构建包、源码归档或标签链接、启动说明、依赖、控制、存档位置、版本说明、兼容/迁移说明、已知问题、校验值、资产授权摘要。

包内具有独立目录、启动入口及可执行权限；不要求用户安装编辑器或在源码目录运行。只列实际运行需要的依赖，不附带开发缓存、临时日志、账户凭据或私有配置。

先验收目标构建，再给同一源码提交打版本标签并创建 Release。正式版若与 RC 内容不同，重新构建并回归变化范围，不能沿用 RC 结果不测。

通过条件：用户解压或安装后可自行启动，从标题经安全房进入完整三区域、结算并开始新局；暂停退出与五存档均正常；附件 B 记录完整且与源码 SHA 一致。

# 阶段 8 持续更新与发布维护

目标：每一次完整可游玩更新都有可追溯记录，修复不破坏已完成体验，内容增加不损坏存档。

## 更新类型

v1.0.x 用于兼容性修复、Bug 修复与小幅平衡；v1.x.0 用于兼容的玩法或内容增加；不兼容的重大存档或接口变化采用新的主版本并明确迁移。0.x 开发版本也必须记录存档 schema 和实际兼容范围，不以版本号推断兼容。

每次更新先建立问题或任务，明确触发场景、当前表现、目标表现、受影响模块与测试。修复优先级高于新增角色和区域；玩家可稳定复现的崩溃或损档优先处理。

## 角色和动作更新

改动骨骼、插槽、碰撞身高或动画事件时，列出全部受影响武器、攻击、技能与敌人交互。新增皮肤应通过完整动作回归，不以立绘通过代替绑定通过。

若调整攻击时长、取消窗口、无敌段或命中停顿，更新数值表和玩家说明；说明对连击、空中动作和原有构筑的影响。美术更新必须标注具体角色和动作，而非笼统写“优化视觉”。

## 存档与回滚

兼容更新保留永久进度；迁移前备份。活动局无法迁移时，告知影响及恢复策略。禁止静默覆盖旧档或以清除所有记录解决问题。

保留旧 Release 和原标签；发布损坏构建时标记撤回，创建修正版，不重新覆盖同一标签附件。回滚前说明新 schema 是否可被旧版读取；不能承诺升级后的存档一定能够降级。

## 每次交付

沿用附件 B 发布门禁。每次发布的更新说明列出新增、调整、修复、美术动作、性能、存档、已知问题与证据。记录修改前后行为、关联任务、提交 SHA 和测试条件。

维护交付：新构建、新版本记录、回归矩阵、遗留问题、新增资产授权、迁移记录和下一版本范围。若只有文档或分支提交而无新可玩包，应描述为开发进展，不能称为已发布版本。

# 角色模型与动作动画规范

本附件规定玩家角色、普通敌人、精英与首领的美术和动作质量。“人物模型”在此指 2D 角色设定、分层结构、骨骼绑定或逐帧资产以及运行时动画，不要求建立 3D 模型。最终目标是在实机镜头中具有体积、重量和连续动作的角色。

## 一 造型与比例

默认玩家角色为约 4.5—5.5 头身的风格化手绘人物。选择具体比例后，除明确的动作透视与压缩外不得逐帧改变体型。主角实际镜头站立视觉高度初测约 96—128 逻辑像素，以可读性与场景设计最终冻结；贴图可用更高分辨率，不能把导出像素直接当作物理大小。

每名角色制作：全身标准侧视、前后或三分之四参考、头部表情、手部握持、服装拆层、配色、武器比例、剪影、世界单位标尺。主参考给出头高、肩宽、躯干长、腿长、脚底基线及装备尺寸，避免生成多张图后拼接为不一致的角色。

识别优先顺序：整体剪影 → 武器和体态 → 大色块 → 面部和装饰。角色区别不能只依赖发色；暗背景、灰度与小尺寸也应能认出。

画风统一：轮廓线粗细、亮暗块、边缘清晰度和光源一致。禁止半写实脸搭配简单几何四肢、不同动作服饰忽然增减、手指数量异常、武器穿过手掌。

## 二 分层与绑定

骨骼路线的源文件至少分为头、颈、躯干、骨盆、上臂/前臂/手、大腿/小腿/脚、前后发层、衣摆、披风、武器和特效挂点。左右肢体独立；肘、膝、肩等关节提供遮盖或合理网格变形。

最低挂点：主手、副手、武器柄、刀尖/枪尖、发射口、头部、脚底、躯干受击位置。箭矢、枪弹、法术由挂点发出，不能从角色中心凭空生成。双手武器维持副手接触，单手武器不得由同一姿势假装双手挥动。

绑定交付包含骨骼层级、约束、插槽命名、默认姿势、动画轨道、导出配置。大幅挥砍、透视和表情允许替换绘制帧；禁止使用极端骨骼拉伸近似高质量手绘动作。

逐帧路线须保持统一画布和锚点，每帧有完整轮廓，不裁切头发、武器或特效。空帧、重复停帧可按时序有意使用，但不能为了凑帧数重复贴同一张静态人物。

## 三 动作清单与预算

下表为基础生产目标。逐帧数量是建议的独立绘制姿势预算；骨骼动画以时序和关键姿势验收，不要求机械对应相同绘制数量。运行帧率、骨骼采样率与绘制帧率是三件事。

| 动作 | 建议姿势/关键帧 | 动作内容与时序要求 |
| --- | --- | --- |
| 待机 | 8—12 | 呼吸、重心和衣摆轻动，脚底不漂移；约 1.2—2 秒循环 |
| 起步 | 3—5 | 重心前移、蹬地，快速进入跑步 |
| 跑步 | 8—12 | 接地、下沉、蹬伸、腾空，左右交替；步频随速度变化 |
| 急停 | 3—5 | 身体惯性与衣摆延迟，不能滑行数个身位 |
| 地面转向 | 3—5 或短混合 | 体态回转与武器归位；不阻塞方向响应 |
| 起跳 | 3—5 | 下压和蹬伸；预备不得延迟即时跳跃响应 |
| 上升 | 2—4 | 重心伸展、腿部收起、衣发滞后 |
| 最高点 | 2—3 | 轻微悬停姿态，不能暂停物理模拟 |
| 下落 | 3—5 | 身体及衣物随速度变化，预备接地 |
| 轻落地 | 3—5 | 膝盖缓冲，短过渡，支持输入缓冲 |
| 重落地 | 5—7 | 更大下沉和回弹；若有硬直须明确条件 |
| 闪避/翻滚 | 6—10 | 预备、位移、恢复；无敌与视觉事件对齐 |
| 地面攻击第 1/2/3 段 | 每段 6—10 | 独立蓄势、挥动、命中与收势，方向和重量逐段变化 |
| 空中攻击 | 6—10 | 与地面动作不同的重心、腿部姿态与轨迹 |
| 重击或蓄力 | 8—14 | 蓄力阶段可循环，释放及收势独立 |
| 独有技能 | 8—16 | 预备、生效、持续/移动、结束，动作揭示能力用途 |
| 轻受击 | 3—5 | 短反应，方向来自伤害源，角色可迅速恢复 |
| 重受击/击倒 | 6—10 | 后仰或击飞、落地，按规则进入起身 |
| 起身 | 5—8 | 支撑、恢复重心，有明示保护规则 |
| 死亡 | 8—12 | 受击失衡、倒地、停止；不只是透明渐隐 |
| 交互/拾取 | 4—6 | 可中断的触碰或拾取，避免战斗中强制长演出 |
| 出生/传送 | 6—10 | 出场结束后交还控制，位置与碰撞安全 |
| 胜利/选择展示 | 8—12 | 角色个性动作，不影响实战动作预算 |

正式版每名玩家角色至少覆盖上表适用动作。空中转向通过朝向和姿态响应完成，不必强制新增一段耗时动画。若不设计击倒系统，可合并重受击与起身，但须记录行为和动画如何覆盖，而非留下缺省动作。

普通敌人最低清单：待机、移动、察觉/瞄准、每个招式的预备/生效/恢复、受击和死亡；飞行、盾兵、召唤者增加对应专属动作。首领每个招式独立制作，并增加登场、阶段切换、失衡或暴露窗口和死亡。

## 四 关键姿势与发力

挥砍应能看到蹬地、髋转、躯干带肩、手臂随动、武器到达、惯性收势。突刺体现身体前压与手臂延伸；弓体现抬弓、拉弦、蓄力、放弦和回位；符铳体现举枪、瞄准、击发和后坐；施法体现聚能、引导、释放和收束。

重武器比轻武器有更强预备、较大身体位移和更长恢复，但控制响应不能拖沓。空中攻击保留腾空重心，脚不能像站地面一样持续踩住隐形平面。

跑步接地脚在接地段尽量保持世界位置，按速度调步频而非横向滑动；落地先腿和骨盆吸收力量，再由上身与衣物跟进。

## 五 动画和玩法时序契约

每个攻击有唯一动作 ID，配置总时长、预备段、生效段、恢复段、命中事件、允许转向段、位移曲线、连击窗口、取消窗口、被打断规则和攻击实例 ID。

示例设计初值：轻刃第一击 0—70ms 预备，70—130ms 生效，130—300ms 收势；可在 150—270ms 接收下一段连击，150ms 后允许闪避取消。时间必须与实际动作、移动及角色平衡一起调整。不能把这个示例直接套给全部武器。

伤害生效须和武器轨迹、弹丸出生或法术区域形成一致。禁止全动画期间开启攻击框。多段技能每一段有明确命中计数规则；命中停顿不重复触发动画事件。

攻速变化按分段规则缩放；需要保留最低预备与恢复以保证可读性。定格、暂停、失焦、慢动作和低帧率都应保持事件只触发规定次数。导出后须再验证，不只在动画编辑器里检查。

## 六 状态、取消与打断

核心状态包括：待机、移动、起跳/上升/最高点/下降/落地、闪避、攻击、技能、受击、击倒/起身、死亡、交互和传送。

| 当前状态 | 可执行操作 | 限制 |
| --- | --- | --- |
| 待机/移动 | 跳跃、攻击、闪避、技能、交互 | 根据资源和接触条件 |
| 上升/下降 | 空中攻击、允许的空中技能/闪避、转向 | 空中次数与资源上限明确 |
| 攻击预备/生效 | 缓冲下一段，特定允许段转向 | 不默认全段取消 |
| 攻击收势 | 连击、闪避，部分技能 | 按武器窗口执行 |
| 闪避 | 朝向响应及动作缓冲 | 位移中不任意叠加攻击 |
| 受击/击倒 | 按规则恢复 | 输入不瞬间消除硬直 |
| 交互 | 移动或闪避中断 | 不丢失领取事务 |
| 死亡 | 结算/返回标题 | 不接受战斗指令 |

优先级默认死亡最高；受击是否打断取决于霸体、无敌和伤害规则；剩余技能、攻击、移动由明确窗口决定。暂停是系统状态，不参与角色动作竞争。禁止把“新输入直接替换当前动画”作为所有状态规则。

## 七 朝向、武器与装备

左右翻转需以统一脚底/骨盆锚点进行，防止转向时跳位。非对称披风、佩饰、护手或文字纹样视美术要求制作左右版本或单独处理，不能让关键设定因镜像错乱。

武器视觉尺寸不改变角色实体碰撞。短刃、重剑、长枪、弓、符铳、法器有各自握持姿势和发射/挥击挂点；持武器待机、跑步、跳跃至少通过叠加或专用姿态正确覆盖。

默认护甲和饰品先采用图标及特效反馈，不承诺每件装备都改变完整服装；若制作可视装备，则每件必须通过全部动作兼容测试。新皮肤保持玩法碰撞和时窗，避免外观带来额外命中优势。

## 八 判定和尺寸

站立实体碰撞以固定 H 和宽度定义；角色全身视觉边缘不自动当作受击区。脚底基线、武器插槽和受击框使用引擎坐标记录，导出裁切或透明边界变化不能移动锚点。

受击框可按闪避、倒地等状态调整，但规则可见并与无敌分开；攻击框随轨迹或独立形状控制。大披风、长发与纯视觉特效不扩大受击范围。

翻滚期间若改变实体尺寸，需测试墙角和低顶恢复，不能恢复站立时嵌入墙体。坡面、台阶、快速落地及镜像都检查接地与判定。

## 九 输出文件和登记

命名建议：角色ID_动作ID_武器族_方向_资产版本。骨骼资产交付源文件、纹理、骨骼/动画数据与工具版本；逐帧交付源文件、透明 PNG 或图集与帧序/时长/锚点元数据。项目规格选择其一，不强制把骨骼动画再转成巨大逐帧图集。

发布纹理使用透明背景，无绿边、白边、裁切和渗色；图集留足边缘扩展，过滤设置按实际缩放验证。源资产备份与版本记录不可遗漏。

登记字段：资产 ID、所属角色、动作、武器、方向、尺寸/世界尺度、锚点、时长、帧或轨道数量、事件时刻、循环/打断规则、作者或来源、授权、源文件、导出文件、预览、审核结论及关联提交。

## 十 验收方法

1. 对照角色参考检查全部动作的头、手、服装、配色和武器身份一致。
2. 实机 1 倍画面观察剪影、脚底、发力、预警与动作可读性；再用慢放检查事件和命中框。
3. 快速切换跑、跳、攻击、闪避、受击，覆盖左右朝向、地面/空中、30/60/120 FPS。
4. 执行 100 次动作转换抽测，无卡姿势、脚漂移、插槽跳动、事件重复或永久失控。
5. 检查角色和全部武器家族组合；共享动画可按基础骨架测试再抽测每件视觉资产，不能省略差异显著的长枪和双手武器。
6. 用灰度、暗场和多特效场景检查敌我可读性；关闭特效后动作仍然能表达攻击。
7. 动画表现、玩法判定、技术稳定、来源授权四项分别判定。任一阻塞未通过，就不能把该资产标为正式完成。

审核结果必须有具体证据和待修列表。最终玩家角色不允许以“后续补动作”为由发布缺失的基础动画。

# GitHub 与版本发布规范

目的：后续游戏代码接入当前已绑定 GitHub 账号，每一次可游玩版本都记录做了什么、如何验证、如何下载与恢复。

## 账号和仓库

本次通过当前 GitHub 连接只读核验，登录名为 `doomsdayend`。执行开发时再次读取连接身份，不能凭历史用户名代替当前身份。暂定专用私有仓库 `doomsdayend/emberbound-2d-roguelite`，未创建、未检查名称可用性；重名时采用明确后缀并记录实际 URL。

权限不足或没有仓库创建能力时，应说明阻塞和具体所需操作；不要更换账号、暴露 Token 或把内容写到现有不相关仓库。若有多个绑定身份且当前身份无法确定，再由用户选择。

仓库从阶段 1 开始保存需求与设计，后续加入项目源码和资源。工作目录建议包括 docs、assets/source、assets/exported、game、tests、tools 和 releases 的说明/元数据。实际目录按引擎调整，不把发布二进制长期提交到普通 Git 历史；使用 Release 附件，大源文件按方案管理。

## 提交与开发记录

默认 main 保持最近一次通过验证的状态，阶段工作用独立分支，通过 PR 或明确评审后合入。提交按可理解的功能单元组织，描述改变及原因；不要每次直接堆成“update”。

每阶段任务关联需求 ID，每次 PR 说明：触发问题、最终行为、主要修改、实际运行测试、存档影响和遗留风险。架构、范围、角色风格和生成算法改变须追加决策记录。

建议需求 ID：SYS 系统、ACT 动作、ART 美术、COM 战斗、MAP 地图、ROG 构筑、SAV 存档、REL 发布；需求表记录阶段、优先级、验收与证据位置。

## 发布对象和版本

每个完整可游玩构建，不论原型、Alpha、Beta、RC 或正式版，都必须具有唯一版本。开发中可玩版本使用 v0.x.y；正式版之后用 v1.x.y。Alpha/Beta/RC 在标题和 Release 中清楚标记，必要时使用预发布标识。

标签固定到通过验证的源码 SHA；不能移动旧标签。补发修复使用新版本。失败发布不能写为成功，未上传附件的 Release 不能算完成发布。

## 每次发布步骤

1. 冻结版本范围，关闭 P0/P1 或按早期原型门槛明确限制；确认该版本可玩流程。
2. 在候选提交构建目标平台包，记录引擎和依赖版本、构建配置与时间。
3. 对同一个候选包完成干净环境启动、主流程、关键动作、存档与暂停回归。
4. 填写更新说明和测试报告，更新 CHANGELOG、兼容表和资产来源；保留实际证据。
5. 以最终文档和源码提交重新构建，至少重跑安装启动与变化范围，记录最终 SHA 和文件校验值。
6. 给最终 SHA 创建版本标签与 GitHub Release，附构建、源码入口、更新说明和 SHA-256。
7. 核验 Release 页面、版本、附件和 SHA 对应，下载附件检查大小与校验值；必要时再次启动发布附件。
8. 在发布台账登记真实链接和结果。不凭“上传命令已提交”宣布成功。

流程可以由 CI 自动完成，但没有自动化能力时仍需手动遵守。文档不假设当前环境已经具备创建仓库、标签或 Release 的工具。

## 必须保存的记录

- CHANGELOG.md：按版本列新增、调整、修复、美术动作、性能、存档变化和已知问题，链接详细发布说明。
- docs/releases/<版本>.md：具体修改前后行为、角色动作清单、测试条件、源码 SHA、包名和校验值。
- docs/testing/<版本>.md：测试环境、用例、预期与实际结果、复现种子、人工验证和未覆盖项。
- docs/decisions/：架构、美术标准、范围、存档和算法的关键决策。
- 发布台账：版本、日期与时区、范围、源码 SHA、Tag、Release、附件、兼容、测试结论、回滚版本。

更新记录不能只有“修了一些 Bug”。例如：“烬刃第三击在收势中接闪避会丢失输入；现允许指定窗口缓冲，补充恢复姿态；30/60/120 FPS 下左右转向均验证”。仅记录真实完成的修改。

## 安全与授权
